# OpenH264：AArch64 NEON SAD 优化

[English](README.md) · [上游 commit](https://github.com/cisco/openh264/commit/6fe62b8f3fcc6bf34512be7efc7f64e91f510f02) · [PR #4041](https://github.com/cisco/openh264/pull/4041)

**改动已于 2026-10-09 合并。** 我将 16x8、16x16 SAD 函数改为两条独立累加链，保持计算结果一致。本地复测中，**16x16 单块耗时中位数减少 8.7%，9 组中有 8 组更快**。16x8 和散布访问未见明确收益；本次未测整机编码速度。

## 测试结果

2026-10-28，Apple M1、Clang 21、`-O3`，比较合并提交与其[直接父版本](https://github.com/cisco/openh264/commit/bb7199902306938e7e583d7bcd01be46f10e70c9)。每项测量调用 1 亿次，执行 9 组配对并交替运行顺序；表中为中位耗时。

| 测试 | 优化前 ns/call | 优化后 ns/call | 更快的组数 |
| --- | ---: | ---: | ---: |
| 16x16，单块重复 | 6.845 | 6.251 | 8/9 |
| 16x8，单块重复 | 3.215 | 3.174 | 6/9 |
| 16x16，64 块散布 | 25.865 | 25.636 | 6/9 |
| 16x8，64 块散布 | 11.876 | 11.949 | 2/9 |

两版各通过 **4,608 次与 C 参考实现的精确比较**，覆盖正负步长、非对齐地址、极值和随机像素。计时配对的输出校验和也全部一致。测试未绑定核心，存在调度波动，较小差异不足以认定稳定收益。

## 优化思路

原实现把各行绝对差累加到同一个向量，连续的 `uabal/uabal2` 形成串行依赖。我改为每次处理两行：用 `uabd` 计算字节绝对差，用 `uaddlp/uadalp` 分别累加，最后合并两个向量，让处理器有更多独立指令可调度。

先确认算术边界：16x16 时每个 16-bit 累加通道最大为 8,160，完整 SAD 最大为 65,280，均在对应类型范围内，调整加法顺序不会溢出或产生舍入误差。

**这个改动的价值是缩短计算依赖链，收益取决于访问方式。** 散布访问没有呈现明确改善，说明单块微基准的收益不能直接推算到编码器；进一步判断瓶颈需要性能计数器，整机收益则需要代表性视频测试。
